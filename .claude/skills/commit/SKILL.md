# commit

변경사항을 분석하여 컨벤션에 맞게 커밋한다.

## 모드
- **기본(승인 모드)**: 커밋 계획을 보여주고 사용자 승인 후 커밋한다.
- **자동 모드**: 사용자가 `--auto`를 붙이거나 "승인 없이", "바로 커밋", "묻지 말고 커밋" 등으로 요청하면 승인 단계를 건너뛰고 바로 커밋한다.
  - 분석·분류·메시지 규칙은 승인 모드와 동일하게 따른다.
  - 비밀 파일 제외와, 파일 분리 여부처럼 판단이 모호한 경우(2단계)는 자동 모드에서도 사용자에게 묻는다.
  - 해당 요청 1회에만 적용되며, 다음 요청은 다시 승인 모드다.

## 절차

### 1. 변경사항 분석
- `git status`로 변경/신규(untracked) 파일을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 변경 내용을 읽는다.
- `git log --oneline -10`으로 최근 커밋 메시지 스타일을 참고한다.
- git 저장소가 아니거나 변경사항이 없으면 그 사실을 알리고 중단한다.
- `.env`, 키/토큰, 자격 증명 파일이 변경 대상에 있으면 커밋 대상에서 제외하고 사용자에게 경고한다.

### 2. 논리적 단위로 분류
- 하나의 목적(기능 추가, 버그 수정, 리팩터링, 설정 변경)별로 변경 파일을 묶는다.
- 서로 다른 성격의 변경은 별도 커밋으로 분리한다. 단일 목적이면 커밋 1개로 충분하다.
- 파일 일부만 다른 단위에 속하면 `git add -p` 대신 사용자에게 분리 여부를 물어본다.

### 3. 커밋 메시지 작성 (한국어)
형식:

```
<type>: <요약>

<본문 (선택): 무엇을, 왜 바꿨는지>
```

- type
  - `feat`: 새로운 기능
  - `fix`: 버그 수정
  - `refactor`: 동작 변경 없는 구조 개선
  - `chore`: 빌드, 설정, 의존성, 문서 등 기타
- 요약은 한국어로, 50자 안팎, 마침표 없이 명사형/간결체로 쓴다.
- 본문은 요약만으로 부족할 때만 추가한다.
- 메시지 끝에 시스템 지침이 요구하는 공동 작성자(Co-Authored-By) 줄이 있으면 덧붙인다.

### 4. 커밋 (승인 모드 / 자동 모드)
- **자동 모드**: 계획을 출력만 하고 승인을 기다리지 않고 바로 스테이징·커밋한다.
- **승인 모드**: 아래 승인 절차를 따른다.
- 커밋 계획을 먼저 보여준다: 커밋별 **포함 파일 목록**과 **메시지 전문**.
- (승인 모드) 사용자가 승인(또는 수정 요청)할 때까지 기다린다. 수정 요청이 있으면 반영 후 다시 확인받는다.
- 승인되었거나 자동 모드이면 커밋 단위마다 해당 파일만 `git add <파일>`로 스테이징하고 `git commit`을 실행한다. (`git add -A`/`git add .` 지양)
- 완료 후 `git log --oneline`으로 결과를 보여준다.

## 금지 사항
- 승인 모드에서 승인 없이 커밋 (자동 모드는 허용), `git push`, `--amend`, `--no-verify`, 강제 옵션 사용.
- pre-commit 훅이 실패하면 우회하지 말고 원인을 보고하고 수정한다.
