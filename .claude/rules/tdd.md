# TDD Rule

> **⚠️ 이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 단계를 건너뛰거나, 순서를 바꾸거나, 일부만 골라 적용하지 않는다. 그대로 따른다.

## 0. 우선순위 (Fallback)

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 침묵하거나 충돌하지 않는 부분에만 적용한다.

## 1. 적용 기준

### TDD 필수

- 비즈니스 로직
- API (엔드포인트, 핸들러, 서버 로직)
- 유틸 함수
- 버그 수정 (**재현 테스트를 먼저 작성**하고 실패를 확인한 뒤 고친다)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

> 판단이 애매하면 **적용 대상으로 간주**한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유는 **"기능이 구현되지 않아서"** 여야 한다. 오타, import 오류, 설정 오류로 인한 실패는 RED가 아니다 — 먼저 고친다.

### GREEN — 통과시키는 최소 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. (**YAGNI**: 지금 필요 없는 건 쓰지 않는다)
- **신규 테스트 + 기존 테스트 전체가 통과**하는지 실행해서 확인한다.

### REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출.
- **항상 green 상태를 유지**한다. 변경 후마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 한다.

### 반복

- 다음 동작이 있으면 **RED로 돌아간다.**

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 복사해 두기 모두 포함한다.
- 삭제한 코드를 보고 다시 쓰는 것도 안 된다. 테스트가 요구하는 것만 새로 쓴다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 쉽게 깨진다. 테스트도 30초면 쓴다. **단순하면 테스트 비용도 낮다.** |
| "나중에 추가하겠다" | 나중은 오지 않는다. 사후 테스트는 구현을 그대로 베끼므로 **버그를 잡지 못한다.** |
| "시간이 없다" | 디버깅과 회귀 수정이 훨씬 오래 걸린다. **TDD가 더 빠른 길이다.** |
| "삭제하면 낭비" | 매몰 비용 오류다. 검증 안 된 코드를 유지하는 비용이 더 크다. **삭제 후 재작성은 빠르다.** |
| "프로토타입이다" | 프로토타입은 곧 프로덕션이 된다. **버릴 코드라면 더더욱 삭제 비용이 없다.** |
